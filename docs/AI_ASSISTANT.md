# AI asset assistant

Available in v0.60.0. In Chat choose **AI assistant**, pick a configured OpenAI,
Claude or Gemini connection and model, and enable external AI access in Settings.
Then write ordinarily:

- "I own a Makita drill, model DHP484, serial 0012345. Its battery type is 18V LXT."
- "My F150's tire size is 205/55R16 and its paint is Oxford White."
- "What color is my bicycle?"
- "My garage fridge is an appliance; its filter specification is EDR1RXD1."

The model chooses among a small set of tools: search your current assets, read
one asset's current details, type and saved web research, list your asset types, add one owned asset,
save several details (and optionally its type) on one asset, ask you a question,
or answer. LifeGather validates and performs every
write; the model never sees an account ID, database query or unrestricted tool.
**Local assistant (no AI)** keeps the existing offline commands and never
contacts a provider.

## What is checked before saving

- Each value, name, manufacturer, model and serial must appear in your own words
  (this message or the earlier message a pending question came from). Invented,
  normalized or looked-up values are refused and nothing is saved.
- Adding an item needs your own words stating current ownership. Model and serial
  need a manufacturer. Possible duplicates produce a choice; only your answer to
  that question can add a separate item or link to a listed existing one.
- All details in one request are saved together or not at all. Several current
  statements for the same detail, or a record that changed after it was read,
  stop the request with an explanation.
- Asset IDs must come from this request's searches/reads, the selected record or
  the pending question. Another account's records are never readable.
- One write per request, at most 6 model replies and 8 reads, bounded context.

## Saved web research (v0.88.0)

Ask, for example, "What filter did I save research about for my mower?" Select
the asset or name it in your request. The model can choose
`read_asset_research(asset_id)` after identifying the item. Existing configured
external-AI permission applies, including sending the saved excerpts to that
provider. This reads your saved findings without starting research or visiting
the web.

The tool reads at most five findings across the request, newest saved first for
each asset it reads, within an 8,000-byte UTF-8 citation budget. Long URLs and
multilingual excerpts can reduce the selection further. Removed findings are
excluded, and consolidated records use
their current physical identity group. Repeated reads reuse earlier context.
An explicit selection notice means more findings may exist; use the asset's
**Saved web research** panel to inspect the larger list. Empty results mean no
active findings were read, not that no manual exists online.

Replies display **Saved research inspected**, with page date (when reported),
research/save times, saved excerpts, source links and **Open <asset> saved
research**. A prior generated answer excerpt is labeled separately from a source
excerpt. These citations are host-owned snapshots of what was read for that
reply; later removal or identity correction does not rewrite historical replies.
Use the asset panel to see current saved findings. The model is instructed to
cite `[Research N]`, state uncertainty and explain when excerpts are insufficient.

Research describes a product model and never establishes ownership, purchase
details or parts compatibility. After a successful research read, the whole turn
is read-only: asset writes and email scan enqueue are refused by the host. Supply
details in a fresh request for a write; the existing user-word and supplied-file
checks still apply. Research text cannot supply values or authorize writes.
Reading full manuals, saving researched values and global research search remain
outside this increment. Tests use synthetic providers; live answer quality is
unverified. No new schema, dependency, permission or automatic action.

The reply after a save is generated by LifeGather from the committed result, with
**Open** and source links; the model cannot claim a save that did not happen.
Questions and answers always say when nothing was saved.

## Asset types and typed fields

Since v0.63.0 the assistant can assign one of your current asset types (starter
or custom) and save that type's field values, such as a Vehicle's tire size or an
Appliance's filter specification, in the same all-or-nothing request as other
details. Reading an asset shows its type fields by name.

- The type must be one LifeGather listed in this request and you must name it in
  your own words ("it's a vehicle", "file it under electronics"). The assistant
  asks rather than guessing a type from the item's name.
- Changing a type replaces the single current assignment and keeps the earlier
  one in history. Several current type assignments must be resolved on the asset
  page first.
- Type field values must appear exactly in your words and belong to the assigned
  or newly chosen type. Retired types and fields take no new values; a VIN still
  uses the standard VIN detail. Editing type definitions stays on the Types page.

## Evidence and history

Your message is saved as the source for every detail, and asset entries record
the provider/model and your ownership words. Change history shows the method
**ai assistant**. Updated details keep their earlier statements as history.
Replaying the same request returns the stored outcome without another model call.
Stopping a request before its write commits prevents the write.

## Progress while it works

Since v0.61.0 Chat shows short progress lines while an assistant request runs, such
as "Searching your assets…" or "Checking details before saving…". LifeGather
writes these itself at each tool-loop stage; they never contain model text or
reasoning and never claim that anything was saved. The reply, and any saved
result, appears only once the request's turn is committed. Stopping, retrying and
replaying behave as before.

## Email scans

Available in v0.62.0. Ask, for example, "Find purchases in my Gmail from last
week" or "Import my email text from March 1 to March 10 as evidence only, up to 5
messages." The assistant can list your connected Gmail mailboxes and queue one
existing scan:

- **Purchase discovery** (`gmail_discovery`) uses the same AI connection and
  model as the assistant to propose purchases from email text, exactly like
  enabling discovery in Scans.
- **Evidence only** (`gmail_import`) saves original email text with no AI call
  and no inventory changes.
- **Attachments** (`gmail_attachments`, v0.77.0) saves supported attached
  documents to Documents for text review, with no AI call; see
  [attachment intake](EMAIL_SCANS.md#attachment-intake-v0770).

Before anything is queued, your own words must state what to look for and which
days; the model turns that period into dates, and the reply shows the exact UTC
days, mailbox and message limit used. With several connected mailboxes you must
name the address. Scans cover at most 31 past days and 20 messages unless you
state another number (up to 50); attachment scans default to 10 and allow up to
20. Text scans omit attachments. The existing
mailbox, external-AI permission, one-active-scan and 20-runs-per-day checks
still apply, and the scan is queued in the same commit that completes the chat
turn. **View email scan** opens its progress, evidence and cancel control.
Replaying the request returns the same scan.

## Pending questions

A question the assistant asks is saved with the turn. Only your next message in
the same conversation can answer it; a new conversation, a later question, a
refused write or a changed record ends it.

## Limits

- One physical asset or one email scan per request; no batch entry, deletion,
  merging or type definition editing (use the asset and Types pages for those).
- Home/place profiles are not edited by the AI assistant.
- Ask AI remains the cited evidence-recall mode; assistant answers about records
  use only the details it read in that request.
- Synthetic scripted-provider tests cover the tool loop. Real model quality has
  not been verified against live providers.

## Photos and documents

Available in v0.69.0. In **AI assistant** choose **Attach a photo** or **Attach a
document**, pick one of your saved originals, then ask about it or say what to
save: "What serial is on this plate?" or "Save the model and serial from this
manual to my drill." Choosing a file makes no AI request.

Since v0.92.0 **Attach a photo** opens your saved photos straight away as small
square thumbnails (twelve at a time, **More saved Chat photos** for the rest),
the chosen photo shows as a thumbnail before you send, and your message in the
conversation keeps showing which photo or document you attached, also after a
reload. A file carried over to your answer to the assistant's question is not
shown again on that answer.

- `read_attachment` gives the model the file's text: a document's saved (or
  corrected) text, otherwise its locally extracted text, or a photo's saved
  transcription. A photo without one is sent to your selected provider once to
  transcribe; that transcription is saved as the photo's source and reused by
  later requests, Photos and the existing reading actions.
- File text is untrusted data, never instructions. Answers about it say
  "No changes were saved."
- A saved value must appear exactly in your words or in the text the assistant
  read in this request. A detail found only in the file cites the file's own
  source, so its evidence link opens the original photo or document. A document
  whose text was never saved gets its extracted text (first 4000 characters)
  saved as its source in the same commit as the detail; reading alone saves
  nothing.
- The file never establishes ownership, which asset it belongs to, or the asset
  type: those still need your own words. Adding a new item from a file keeps the
  file text in the entry's source alongside your ownership words.
- Saving details from a photo also shows it in that asset's photo gallery.
- A question the assistant asks about the file keeps it for your answer. Missing,
  deleted or another account's files are refused before any AI request.
- One file per message. Replays return the saved outcome without reading or
  transcribing again.
