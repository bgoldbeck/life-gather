# Real visitor addresses behind the Cloudflare test site (Phase 5.4)

Goal: behind the `deploy/cloudflare` Worker, sign-in rate limits and logs see
each visitor's own address instead of one shared address, without trusting
forwarded headers from anyone but the Worker. Self-hosting is unchanged.

## Scope
- New optional setting `LIFEGATHER_PROXY_SECRET` (32+ visible ASCII
  characters, empty by default). When set, a request carrying the header
  `X-LifeGather-Proxy-Secret` with exactly that value (constant-time compare)
  may set the client address from a single valid `X-Forwarded-For` IP and the
  scheme from `X-Forwarded-Proto` (`http`/`https`). Anything else is ignored.
- The secret header is always removed before the app sees the request.
- The Cloudflare Worker gets a required `PROXY_SECRET` (generated by
  `npm run init-settings`), passes it to the container, drops any visitor copy
  of the header and adds its own next to `CF-Connecting-IP`.
- `LIFEGATHER_TRUSTED_PROXIES` keeps working as before; `0.0.0.0/0` is still
  not used for the test site. The secret is deployment-local and never enters
  recovery bundles.

## Acceptance checks
- Backend tests: no secret means forwarded headers are ignored; right secret
  sets client and scheme; wrong/missing secret, malformed or multi-value
  addresses are ignored; the header never reaches the app; weak secrets are
  refused; trusted-proxies behaviour unchanged; recovery capture still passes.
- Worker tests: visitor-supplied secret header is replaced; secret is required
  and mapped into the container settings.
- Full backend suite on PostgreSQL, mypy/ruff, Worker tests and typecheck.
